# Работа с приложениями в кластере

> Написано как практическое задание по документированию. Названия сервисов и окружений в примерах условные.

Руководство для разработчиков, которые разворачивают и обслуживают свои приложения на платформе.

## Введение

Платформа запускает приложения в кластере Kubernetes. Основной инструмент работы — утилита командной строки `kubectl`: она отправляет запросы к кластеру и показывает результат.

**Что нужно перед началом работы:**

- установленная утилита `kubectl` — см. [Установка kubectl](https://kubernetes.io/ru/docs/tasks/tools/);
- файл доступа к кластеру (kubeconfig) — его выдаёт команда эксплуатации;
- права на тот namespace, в котором вы работаете.

**Как проверить, что доступ настроен.** Выполните:

```bash
kubectl cluster-info
```

Если в ответе появился адрес control plane, доступ есть. Если команда сообщает об ошибке подключения — см. раздел [Частые проблемы](#частые-проблемы-и-их-решения).

Все примеры в руководстве приведены для окружения разработки — namespace `development`.

## 1. Обзор кластера

Кластер состоит из управляющего слоя (control plane) и рабочих узлов, на которых выполняются приложения. Управляющий слой принимает команды, хранит описания ресурсов и следит за тем, чтобы фактическое состояние кластера соответствовало описанному.

**Как посмотреть основные адреса кластера:**

```bash
kubectl cluster-info
```

Пример вывода:

```
Kubernetes control plane is running at https://cluster.example.com:6443
CoreDNS is running at https://cluster.example.com:6443/api/v1/namespaces/kube-system/services/kube-dns:dns/proxy

To further debug and diagnose cluster problems, use 'kubectl cluster-info dump'.
```

Что здесь важно:

| Компонент | Адрес | Назначение |
|---|---|---|
| Control plane | `https://cluster.example.com:6443` | Точка входа в кластер. Сюда обращается `kubectl` и все инструменты автоматизации |
| CoreDNS | служба в namespace `kube-system` | Внутренний DNS кластера. Благодаря ему приложения обращаются друг к другу по именам, а не по IP-адресам |

Ресурсы кластера разделены на namespaces — логические разделы (подробнее в разделе [Работа с namespaces](#2-работа-с-namespaces)). В нашем кластере их семь:

| Namespace | Назначение |
|---|---|
| `development` | Окружение разработки. Здесь разработчики разворачивают и проверяют свои изменения |
| `staging` | Предпродакшн. Проверка релиза на конфигурации, близкой к боевой |
| `production` | Боевое окружение. Обслуживает реальных пользователей |
| `default` | Namespace по умолчанию. Приложения платформы здесь не размещаются |
| `kube-system` | Служебные компоненты Kubernetes: DNS, сетевые агенты, контроллеры. **Изменять его содержимое нельзя** |
| `kube-public` | Служебный namespace с общедоступной информацией о кластере |
| `kube-node-lease` | Служебный namespace, через который узлы сообщают кластеру, что они живы |

Разработчику нужны, как правило, только `development` и `staging`. Доступ к `production` выдаётся отдельно.

## 2. Работа с namespaces

Namespace — логический раздел кластера. Ресурсы одного namespace не пересекаются с ресурсами другого по именам, поэтому приложение `auth-service` может одновременно существовать и в `development`, и в `production`.

### 2.1. Как посмотреть список namespaces

```bash
kubectl get namespaces
```

Пример вывода:

```
NAME              STATUS   AGE
default           Active   365d
kube-node-lease   Active   365d
kube-public       Active   365d
kube-system       Active   365d
development       Active   180d
production        Active   180d
staging           Active   180d
```

Столбцы:

- **NAME** — имя namespace;
- **STATUS** — состояние. `Active` — рабочее состояние. `Terminating` означает, что namespace удаляется и создавать в нём ресурсы уже нельзя;
- **AGE** — сколько времени существует namespace.

Сокращённая форма команды — `kubectl get ns`.

### 2.2. Как создать namespace

```bash
kubectl create namespace my-feature
```

Или декларативно, через манифест — этот способ предпочтителен, потому что файл можно хранить в репозитории вместе с остальной конфигурацией:

```yaml
# namespace.yaml
apiVersion: v1
kind: Namespace
metadata:
  name: my-feature
```

```bash
kubectl apply -f namespace.yaml
```

> **Важно.** Создание namespace обычно требует расширенных прав. Если команда завершается ошибкой `forbidden`, обратитесь в команду эксплуатации.

### 2.3. Как переключиться между namespaces

Есть два способа.

**Способ 1. Указать namespace в конкретной команде** — флаг `-n` (или `--namespace`):

```bash
kubectl get pods -n development
```

Подходит, когда нужно однократно заглянуть в чужое окружение.

**Способ 2. Сменить namespace по умолчанию для текущего контекста:**

```bash
kubectl config set-context --current --namespace=development
```

После этого флаг `-n` можно не указывать: все команды будут выполняться в `development`.

**Как проверить текущий namespace:**

```bash
kubectl config view --minify --output 'jsonpath={..namespace}'
```

Если команда ничего не вывела, действует namespace `default`.

> **Совет.** Прежде чем выполнять команды, изменяющие состояние (`apply`, `delete`, `scale`), проверяйте текущий namespace. Это самая частая причина изменений, внесённых не туда, куда планировалось.

**Как посмотреть ресурсы во всех namespaces сразу** — флаг `-A` (или `--all-namespaces`):

```bash
kubectl get pods -A
```

## 3. Деплойменты: какие приложения запущены

Deployment описывает, какое приложение и в каком количестве копий должно работать. Он создаёт поды по заданному шаблону и поддерживает их количество: если под упал или узел вышел из строя, Deployment создаёт замену.

### 3.1. Как посмотреть список деплойментов

```bash
kubectl get deployments -n development
```

Пример вывода:

```
NAME                   READY   UP-TO-DATE   AVAILABLE   AGE
auth-service           2/2     2            2           45d
api-gateway            3/3     3            3           90d
user-service           2/2     2            2           60d
payment-service        1/1     1            1           30d
notification-service   1/1     1            1           15d
```

### 3.2. Как читать вывод

| Столбец | Что означает |
|---|---|
| **NAME** | Имя деплоймента |
| **READY** | Готовые копии из запрошенных, в формате «готово/запрошено». `2/2` — обе копии работают и принимают трафик. `1/2` — одна копия ещё не готова: приложение либо запускается, либо не может запуститься |
| **UP-TO-DATE** | Сколько копий обновлено до текущей версии шаблона. Если значение меньше, чем в `READY`, идёт обновление |
| **AVAILABLE** | Сколько копий доступно достаточно долго, чтобы считаться стабильными |
| **AGE** | Сколько времени существует деплоймент — не путать с временем работы подов |

**Признак здорового деплоймента:** все три числа — `READY`, `UP-TO-DATE`, `AVAILABLE` — совпадают с запрошенным количеством копий.

### 3.3. Приложения окружения development

Все пять сервисов доступны внутри кластера на порту 8080 через сервисы типа ClusterIP — то есть только для других приложений кластера, снаружи они недоступны.

| Приложение | Копий | Внутренний адрес | Назначение |
|---|---|---|---|
| `api-gateway` | 3 | `api-gateway:8080` (10.96.100.20) | Точка входа для внешних запросов, маршрутизация к остальным сервисам. Копий больше всего, потому что через него проходит весь трафик |
| `auth-service` | 2 | `auth-service:8080` (10.96.100.10) | Аутентификация и выдача токенов: вход, выход, обновление токена |
| `user-service` | 2 | `user-service:8080` (10.96.100.30) | Данные пользователей |
| `payment-service` | 1 | `payment-service:8080` (10.96.100.40) | Платежи |
| `notification-service` | 1 | `notification-service:8080` (10.96.100.50) | Отправка уведомлений |

Обращаться к сервису из другого приложения кластера следует по имени, а не по IP-адресу: `http://auth-service:8080`. IP-адрес сервиса может измениться при пересоздании, имя — нет.

### 3.4. Как посмотреть список сервисов

```bash
kubectl get services -n development
```

Пример вывода (столбец AGE опущен):

```
NAME                   TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)
auth-service           ClusterIP   10.96.100.10   <none>        8080/TCP
api-gateway            ClusterIP   10.96.100.20   <none>        8080/TCP
user-service           ClusterIP   10.96.100.30   <none>        8080/TCP
payment-service        ClusterIP   10.96.100.40   <none>        8080/TCP
notification-service   ClusterIP   10.96.100.50   <none>        8080/TCP
```

`EXTERNAL-IP: <none>` означает, что напрямую из интернета сервис недоступен. Внешний доступ настраивается отдельно — через Ingress или сервис типа LoadBalancer.

### 3.5. Как посмотреть подробности о деплойменте

```bash
kubectl describe deployment auth-service -n development
```

Команда покажет версию образа, стратегию обновления, лимиты ресурсов, условия готовности и последние события — например, из-за чего не удалось создать под.

## 4. Проверка статуса подов

Под — минимальная единица запуска. Одна копия приложения работает в одном поде.

### 4.1. Как посмотреть список подов

```bash
kubectl get pods -n development
```

Пример вывода:

```
NAME                                  READY   STATUS    RESTARTS   AGE
auth-service-5f8d9c7b4d-x7k2m         1/1     Running   0          2d
auth-service-5f8d9c7b4d-p9n3q         1/1     Running   0          2d
api-gateway-6c7b8d9f5c-m4k8p          1/1     Running   0          5d
api-gateway-6c7b8d9f5c-n2w7r          1/1     Running   0          5d
api-gateway-6c7b8d9f5c-q1t5s          1/1     Running   0          5d
user-service-7d8e9f0a6d-k3j6h         1/1     Running   0          1d
user-service-7d8e9f0a6d-l5m9n         1/1     Running   0          1d
payment-service-8e9f0a1b7e-o2p4q      1/1     Running   0          12h
notification-service-9f0a1b2c8f-r3s5t 1/1     Running   0          6h
```

В примере все девять подов исправны: статус `Running`, все контейнеры готовы, перезапусков нет.

### 4.2. Как читать имя пода

Имя пода состоит из трёх частей: `auth-service-5f8d9c7b4d-x7k2m`

- `auth-service` — имя деплоймента;
- `5f8d9c7b4d` — идентификатор версии шаблона. У подов одной версии он одинаковый, при обновлении приложения меняется. Удобно, чтобы отличить старые поды от новых во время развёртывания;
- `x7k2m` — случайный суффикс конкретного пода.

Имя пода одноразовое: после пересоздания под получит новое имя. Не сохраняйте его в скриптах — получайте актуальное имя командой `kubectl get pods`.

### 4.3. Как читать столбцы

| Столбец | Что означает |
|---|---|
| **READY** | Готовые контейнеры из общего числа в поде. `1/1` — единственный контейнер работает и прошёл проверку готовности. `0/1` при статусе `Running` означает, что контейнер запущен, но проверку готовности не прошёл и трафик на него не идёт |
| **STATUS** | Состояние пода — см. таблицу ниже |
| **RESTARTS** | Сколько раз контейнер перезапускался. Любое значение больше нуля — повод посмотреть логи. Рядом в скобках может указываться время последнего перезапуска |
| **AGE** | Сколько времени существует под. Значение заметно меньше, чем `AGE` деплоймента, означает, что под пересоздавался: было обновление или перезапуск |

**Основные статусы:**

| Статус | Что значит | Что делать |
|---|---|---|
| `Running` | Под запущен и работает | Ничего |
| `Pending` | Под создан, но не запущен: не хватает ресурсов на узлах, нет подходящего узла или не готов том | Посмотреть события: `kubectl describe pod <имя>` |
| `ContainerCreating` | Загружается образ, создаётся контейнер | Подождать. Если состояние держится долго — смотреть события |
| `CrashLoopBackOff` | Контейнер запускается, падает и перезапускается по кругу | Смотреть логи, в том числе предыдущего запуска |
| `ImagePullBackOff` / `ErrImagePull` | Не удалось скачать образ: опечатка в имени или версии, нет прав к реестру | Проверить имя образа в манифесте и доступ к реестру |
| `Terminating` | Под завершает работу | Подождать. Если состояние держится долго, приложение не обрабатывает сигнал завершения |
| `Completed` | Процесс завершился успешно. Нормально для задач (Job), но не для сервиса | Для сервиса — проверить, что приложение не завершается сразу после старта |
| `OOMKilled` | Контейнер остановлен из-за превышения лимита памяти | Увеличить лимит памяти или искать утечку |

### 4.4. Как посмотреть подробности о поде

```bash
kubectl describe pod auth-service-5f8d9c7b4d-x7k2m -n development
```

Самое полезное в выводе — раздел **Events** в конце: там перечислены события пода в хронологическом порядке. Именно оттуда становится понятно, почему под не запускается: не нашлось узла, не скачался образ, не смонтировался том, не прошла проверка работоспособности.

### 4.5. Полезные варианты команды

**Поды только одного приложения** — фильтр по метке:

```bash
kubectl get pods -n development -l app=auth-service
```

**С указанием узла и IP-адреса пода:**

```bash
kubectl get pods -n development -o wide
```

**Наблюдать за изменениями в реальном времени** — удобно во время развёртывания:

```bash
kubectl get pods -n development -w
```

**Потребление процессора и памяти** (требуется metrics-server):

```bash
kubectl top pods -n development
```

## 5. Просмотр логов

Логи — основной источник информации о том, что происходит внутри приложения.

### 5.1. Базовая команда

```bash
kubectl logs <имя-пода> -n <namespace>
```

Пример — последние 20 строк логов пода `auth-service`:

```bash
kubectl logs auth-service-5f8d9c7b4d-x7k2m -n development --tail=20
```

Фрагмент вывода:

```
2024-01-15 10:23:45 INFO  [main] Starting AuthService application
2024-01-15 10:23:46 INFO  [main] Loading configuration from environment
2024-01-15 10:23:47 INFO  [main] Connecting to database at postgres://db:5432/auth
2024-01-15 10:23:48 INFO  [main] Database connection established
2024-01-15 10:23:49 INFO  [main] Starting HTTP server on port 8080
2024-01-15 10:23:50 INFO  [main] AuthService started successfully
2024-01-15 10:25:12 INFO  [http-handler] POST /api/v1/login - 200 OK - 45ms
2024-01-15 10:26:33 INFO  [http-handler] POST /api/v1/login - 401 Unauthorized - 5ms
2024-01-15 10:28:00 INFO  [http-handler] POST /api/v1/logout - 200 OK - 3ms
```

### 5.2. Как читать строку лога

`2024-01-15 10:23:45 INFO [main] Starting AuthService application`

| Часть | Значение |
|---|---|
| `2024-01-15 10:23:45` | Время события |
| `INFO` | Уровень: `INFO` — обычное событие, `WARN` — предупреждение, `ERROR` — ошибка |
| `[main]` | Источник записи. `[main]` — процесс запуска приложения, `[http-handler]` — обработка входящего запроса |
| дальше | Текст сообщения. Для запросов — метод, путь, код ответа и время обработки |

**Что видно в примере:**

- **Запуск прошёл штатно.** Приложение прочитало конфигурацию, подключилось к базе, поднялось на порту 8080 — всё за пять секунд.
- **Дальше идёт обычная работа:** запросы `POST /api/v1/login`, `/api/v1/refresh` и `/api/v1/logout` с кодом 200 и временем ответа 2–51 мс.
- **Есть две записи с кодом 401 Unauthorized.** Это не сбой приложения: 401 означает, что пользователь ввёл неверные данные для входа. Отдельные 401 в логах сервиса аутентификации — норма. Тревожный признак — их резкий рост: это может говорить об ошибке в клиенте или о попытках подбора пароля.

### 5.3. Полезные варианты команды

| Задача | Команда |
|---|---|
| Последние N строк | `kubectl logs <под> -n development --tail=50` |
| Следить за логами в реальном времени | `kubectl logs <под> -n development -f` |
| Логи за последний час | `kubectl logs <под> -n development --since=1h` |
| Логи **предыдущего** запуска (после падения контейнера) | `kubectl logs <под> -n development --previous` |
| Логи со всех подов приложения сразу | `kubectl logs -n development -l app=auth-service --tail=100` |
| Логи через деплоймент, без выяснения имени пода | `kubectl logs deployment/auth-service -n development` |
| Конкретный контейнер, если их в поде несколько | `kubectl logs <под> -n development -c <контейнер>` |
| Показывать имя пода перед каждой строкой | `kubectl logs -n development -l app=auth-service --prefix` |

**Поиск по логам.** `kubectl` не умеет фильтровать вывод сам, используйте средства оболочки:

```bash
kubectl logs deployment/auth-service -n development --tail=500 | grep ERROR
```

> **Важно.** `kubectl logs` показывает логи только живого пода. Если под удалён и пересоздан, его прежние логи через `kubectl` уже недоступны — флаг `--previous` работает только для перезапуска контейнера в том же поде. Для истории пользуйтесь системой сбора логов платформы.

## Частые проблемы и их решения

### Проблема 1. Команда отвечает «No resources found», хотя приложение работает

**Симптом:**

```
$ kubectl get pods
No resources found in default namespace.
```

**Причина.** Команда выполнена не в том namespace. Без флага `-n` используется namespace по умолчанию — чаще всего `default`, где приложений платформы нет.

**Решение.**

1. Проверьте текущий namespace:

   ```bash
   kubectl config view --minify --output 'jsonpath={..namespace}'
   ```

2. Укажите нужный namespace явно:

   ```bash
   kubectl get pods -n development
   ```

3. Чтобы не повторялось, задайте namespace по умолчанию:

   ```bash
   kubectl config set-context --current --namespace=development
   ```

**Профилактика.** Проверяйте namespace перед командами, изменяющими состояние кластера. Не найти ресурс неприятно, но безопасно; удалить его не в том окружении — гораздо хуже.

### Проблема 2. Под в состоянии CrashLoopBackOff

**Симптом:**

```
NAME                            READY   STATUS             RESTARTS   AGE
payment-service-8e9f0a1b7e-o2p4q  0/1   CrashLoopBackOff   5          4m
```

**Причина.** Контейнер запускается, приложение падает, Kubernetes перезапускает его — и так по кругу, с увеличивающейся паузой между попытками. Типичные причины: ошибка в конфигурации или переменных окружения, недоступная база данных, занятый порт, отсутствующий обязательный параметр.

**Решение.**

1. Посмотрите логи предыдущего запуска — текущий контейнер, скорее всего, ещё не успел ничего записать:

   ```bash
   kubectl logs payment-service-8e9f0a1b7e-o2p4q -n development --previous
   ```

   Ищите последние строки перед падением: обычно там прямо написана причина — например, `Connection refused` при подключении к базе.

2. Если в логах ничего нет, посмотрите события пода:

   ```bash
   kubectl describe pod payment-service-8e9f0a1b7e-o2p4q -n development
   ```

   Обратите внимание на раздел **Events** и на поле **Last State** с кодом завершения. Код `137` означает, что контейнер был остановлен из-за нехватки памяти (OOMKilled) — нужно увеличить лимит.

3. Проверьте, что все нужные ConfigMap и Secret существуют и содержат ожидаемые ключи:

   ```bash
   kubectl get configmap,secret -n development
   ```

4. Устраните причину и примените исправленный манифест. Отдельно перезапускать под не требуется — Deployment создаст новый.

**Как срочно вернуться к рабочей версии,** если поломало обновление:

```bash
kubectl rollout undo deployment/payment-service -n development
```

### Проблема 3. Деплоймент показывает не все готовые копии

**Симптом:**

```
NAME           READY   UP-TO-DATE   AVAILABLE   AGE
auth-service   1/2     2            1           45d
```

Одна копия из двух не готова. Приложение работает, но без запаса: падение второго пода оставит сервис без обслуживания.

**Причина.** Варианты:

- поду не хватает ресурсов и он висит в `Pending`;
- приложение запустилось, но не проходит проверку готовности (readiness probe);
- образ новой версии не скачивается.

**Решение.**

1. Найдите проблемный под — он будет со статусом, отличным от `Running`, или с `READY 0/1`:

   ```bash
   kubectl get pods -n development -l app=auth-service
   ```

2. Посмотрите его события:

   ```bash
   kubectl describe pod <имя-пода> -n development
   ```

   Что можно увидеть в **Events**:

   - `Insufficient cpu` или `Insufficient memory` — на узлах нет свободных ресурсов под запрошенные лимиты. Уменьшите запросы (`requests`) в манифесте или обратитесь в команду эксплуатации;
   - `Readiness probe failed` — приложение запущено, но не отвечает на проверку. Проверьте в манифесте путь и порт проверки; частая ошибка — проверка настроена на порт, отличный от того, который слушает приложение (у наших сервисов это 8080). Если приложение долго стартует, увеличьте `initialDelaySeconds`;
   - `Failed to pull image` — недоступен образ. Проверьте имя и тег.

3. Проверьте состояние развёртывания:

   ```bash
   kubectl rollout status deployment/auth-service -n development
   ```

   Если развёртывание зависло, команда об этом сообщит.

**Профилактика.** Держите не менее двух копий для сервисов, которые обслуживают запросы, и указывайте `requests` близко к реальному потреблению — так планировщику проще найти узел.
